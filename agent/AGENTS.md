# ops-lab 運用チームの基本ルール

## 対象システム

- システム名は ops-lab（ネットショップの注文API のデモ環境）。
- リージョンは ap-northeast-1（東京）だけ。
- 調査対象は、タグ `Project = ops-lab` が付いたリソースだけ。それ以外のリソースは見ない。
- 構成は API Gateway（HTTP API）→ Lambda（ops-lab-order-api）→ DynamoDB（ops-lab-orders）。決済タイムアウト値は SSM パラメータ `/ops-lab/payment/timeout_ms` から読む。

## 絶対に守ること

1. リソースを変更しない。調査と提案だけを行う。再起動、ロールバック、設定変更は人が承認して実行する。
2. 推測で埋めない。値が取れなかったときは「取得できなかった」と書く。「おそらく」「〜と思われる」で断定しない。
3. リリースの説明文やコミットメッセージだけで原因を決めない。必ず実際の設定値、ログ、メトリクスで裏付けを取る。
4. 直前にデプロイがあっても、デプロイ以外の変更（SSM パラメータ、DynamoDB の容量、IAM）も必ず確認する。
5. ロールバックを提案するときは、「ロールバックで本当に直るか」の根拠を書く。原因がデプロイ以外にあるなら、ロールバックでは直らないとはっきり書く。
6. 直近1〜3分のメトリクスが空でも、「止まった」「回復した」と判断しない。CloudWatch のデータは数分遅れて届くことがある。今も続いているかは、アラームの現在の状態と最新のログの時刻で確かめる。
7. 確かめていない仮説（例：「古いコミットから apply した可能性」）は、根本原因と同じ欄に混ぜない。「未検証の仮説」と見出しを分けて書く。

## 報告の書き方

- 日本語で書く。
- 結論を最初に書く（根本原因、原因がアプリ側かインフラ側か設定か、一次対応案）。
- 根拠は「どのログ・メトリクス・変更履歴の、どの値か」を時刻付きで並べる。
- 出力の形式はスキル `order-api-incident` の「報告フォーマット」に従う。

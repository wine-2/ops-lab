# 障害シナリオと検証の進め方

DevOps Agent に3種類の障害を調査させ、「スキルなし」と「スキルあり」で結果を比べる。
勉強会 opsmethod#6 で紹介されていた「教えると賢くなる」を、自分の環境で再現するのが目的。

## 共通の手順

1. `python tools/load.py --url <api_url> --minutes 10` で、ふだんの注文を流しておく（1秒に2件）
2. 2〜3分待ってから、下のシナリオのどれかを起こす
3. アラームが鳴ったら、DevOps Agent に調査させる（Webhook で自動、または Web アプリで手動）
4. 結果を `docs/verification-log.md` に記録する
5. `./tools/chaos.sh reset` で元に戻す

## シナリオ1：設定ミス（config-mistake）

- 何が起きるか：決済タイムアウトの本番値 3000ms が、検証用の 50ms で上書きされる。決済は 80〜400ms かかるので、ほぼ全部の注文がタイムアウトして 504 になる。
- 鳴るアラーム：`ops-lab-api-5xx`、`ops-lab-order-errors`
- 正解：原因は SSM パラメータの変更（設定）。アプリのリリースは関係なく、ロールバックしても直らない。
- 見どころ：直前にデプロイがなくても、設定の変更履歴までたどれるか。

## シナリオ2：バグ入りリリース（bad-release）

- 何が起きるか：バージョン 1.4.0 にクーポン計算のバグが入っている。クーポン付きの注文（約30%）だけが例外で失敗する。
- 鳴るアラーム：`ops-lab-lambda-errors`、`ops-lab-api-5xx`、`ops-lab-order-errors`
- 正解：原因は 1.4.0 のリリース（アプリ）。ロールバックで直る。
- 見どころ：「一部の注文だけ失敗」に気づき、クーポンとの関係まで特定できるか。

## シナリオ3：DB の容量不足（db-throttle）

- 何が起きるか：注文テーブルの書き込み容量が 5 から 1 に下げられる。`--rate 8` の負荷で書き込みが詰まり、503 になる。DynamoDB には使わなかった容量を最大5分ぶん貯めておける仕組み（バースト容量）があるので、詰まり始めるまで数分かかることがある。負荷は10分以上流す。
- 鳴るアラーム：`ops-lab-dynamodb-write-throttle`、`ops-lab-api-5xx`
- 正解：原因は DynamoDB の容量変更（DB）。容量を戻すか、オンデマンドに変える。
- 見どころ：アプリのエラーではなく、DB 側の変更までたどれるか。

## 応用：2つを同時に起こす

シナリオ2のリリース直後にシナリオ1を起こすと、林さんのデモと同じ「デプロイが原因に見えるが、本当は設定」という罠になる。スキルなしで外し、フィードバックとスキルで正解に導けるかを試す。

## 費用の目安

- 1回の検証（10分の負荷）で約1,200リクエスト。Lambda・API Gateway・DynamoDB の無料枠に十分収まる。
- DevOps Agent の調査は1回5〜10分。無料トライアルの範囲で使う（トライアル開始は初めて調査させた時点から）。

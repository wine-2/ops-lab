## #1 シナリオ1（設定ミス）・スキルなし

### 起こしたこと
- 16:47 から1秒2件の注文を流し、16:48:55 に SSM パラメータ `/ops-lab/payment/timeout_ms` を 3000 から 50 に変更
- 16:50:08 にアラーム `ops-lab-api-5xx` が ALARM（変更から約70秒）
- 16:51:19 に Web アプリから調査を開始。依頼文は「アラームが鳴った、根本原因と一次対応案を調べて、環境は変更しないで」だけ

### DevOps Agent の結論（要約）
- 根本原因：16:48:55 に IAM ユーザーが Terraform 管理の SSM パラメータを手作業で 3000→50ms に上書きし、80〜400ms かかる決済が全件タイムアウトした
- 根拠として挙げたもの：CloudTrail の PutParameter、Lambda ログの「timeout_ms=50 をロード」（16:49:06）、PaymentTimeoutError の急増、アクセスログの 504、決済の所要時間は変更前後で変化なし、同じ時間帯に Lambda やデプロイの変更はなし
- 緩和策：パラメータを 3000 に戻す。Lambda の再デプロイや API Gateway の変更は不要（アプリが設定を読み直す作りであることまで把握）
- 再発防止：Terraform と実環境のずれ検知、タイムアウト値の入力制約（allowed_pattern とアプリ側の下限チェック）、Terraform 管理パラメータへの手動変更の IAM 制限と EventBridge 通知

### 気づいたこと
- スキルなしでも、設定の変更履歴までたどって正解した。直前にデプロイがない単純なケースでは、標準の調査能力で十分だった
- 調査中に「Lambda の設定を取得できない（lambda:GetFunction が拒否）」「SSM の現在値と履歴を直接確認できない」という権限の穴を、自分から gap（調べきれなかった点）として報告していた。標準の Agent Space ロールでは読めない情報があり、ログと CloudTrail から間接的に推定していた
- 「apply で戻す」を提案に含めたうえで、Terraform 側で変更を無視する設定（ignore_changes）があることには触れていなかった。コードまでは見ていないため（Agent も gap として申告）

## #2 シナリオ2（不具合のあるリリース）・スキルなし

### 起こしたこと
- 16:59 から1秒2件（うち3割がクーポン付き）の注文を流す
- 17:01:37 に `chaos.sh bad-release` を実行。Terraform で Lambda の説明を v1.3.0→v1.4.0 に、環境変数 FAULT_MODE を coupon_bug にした（コードは同じ）
- 17:02:22 に `ops-lab-lambda-errors`、17:02:54 に `ops-lab-order-errors`、17:03:08 に `ops-lab-api-5xx` が ALARM
- 17:04:01 に調査を開始。依頼文はアラーム名と時刻、「根本原因と初動・恒久対策を」だけで、リリースの話は書いていない

### DevOps Agent の結論（要約）
- 根本原因：17:01:44 に IAM ユーザーが Terraform で Lambda の設定を変え、FAULT_MODE=coupon_bug が有効になった。calc_total() の KeyError 'discount_amount' が未処理のまま 5xx になった
- 根拠：CloudTrail の UpdateFunctionConfiguration、3秒後から続く KeyError、変更前の 2 分間はエラー 0 件、CodeSha256 が直前のコード更新時と同じ（つまり変わったのは設定だけ）、DynamoDB のスロットルは 0
- 影響：17:05:43 までに 126 件の注文が失敗し、保存されていない。成功率は約75%
- 緩和策：環境変数から FAULT_MODE を消す。コードのロールバックは不要。Terraform 管理なので、CLI だけで直すと次の apply で再発すると注意書きつき。手順は「Terraform を止める → 事前確認 → 適用 → アラーム確認 → 戻し方」の5段階
- 恒久対策：Terraform から FAULT_MODE を外す、calc_total を欠損に強くして不正なクーポンは 4xx にする、未処理例外を 5xx に直結させない、障害注入フラグを本番相当から切り離す、エイリアスと CodeDeploy のカナリアで自動ロールバック

### 気づいたこと
- 「v1.4.0 のリリース」という見た目にだまされず、CodeSha256 を比べて「コードは変わっていない、設定だけ」と言い切った。これがこのシナリオで一番見たかった点で、スキルなしで正解した
- lambda:GetFunction は今回も拒否されていたが、CloudTrail の UpdateFunctionConfiguration の中身から FAULT_MODE の値を読み取っていた。ログのスタックトレースから handler.py の行番号まで特定していた
- 直前の別の出来事を、それぞれ切り分けていた。シナリオ1の名残の 5xx（16:49〜16:56、PaymentTimeoutError）は「別のエピソード」、16:58 の Base64 修正デプロイ（UpdateFunctionCode）は「その後 2 分間エラー 0 件なので無関係」と判断した
- gap として「コードリポジトリが未接続なので coupon_bug の分岐を確認できない」「変更前の FAULT_MODE の値が不明」を申告。GitHub を連携すれば、ここも埋まるはず

## #3 シナリオ3（DB の容量不足）・スキルなし

### 起こしたこと
- 17:10 から1秒4件の注文を流す（容量5なので、この時点ではエラーなし）
- 17:12:34 に `chaos.sh db-throttle` を実行。Terraform で注文テーブルの書き込み容量を 5→1 に下げた
- バースト容量があるため、スロットルが出始めたのは約90秒後の 17:14。17:15:08 に `ops-lab-api-5xx`、17:15:54 に `ops-lab-order-errors`、17:16:49 に `ops-lab-dynamodb-write-throttle` が ALARM。Lambda の未処理例外は出ないので `ops-lab-lambda-errors` は OK のまま
- 17:17:48 に調査を開始。依頼文はアラーム名と時刻だけ

### DevOps Agent の結論（要約）
- 根本原因：17:12:41 に IAM ユーザーが Terraform で ops-lab-orders の書き込み容量を 5→1 に下げた。書き込みは約4件/秒あり、上限を超えた分がスロットルされ、PutItem の失敗が 5xx になった
- 根拠：CloudTrail の UpdateTable、Lambda ログの ProvisionedThroughputExceededException、スロットル最大 571件/分、5xx 最大 183件/分、Lambda の未処理例外アラームは OK、オートスケーリングの設定なし
- 緩和策：容量を 1→10 に上げ、Terraform の値もそろえる。5 に戻すだけだと使用率約80%で余裕がないため 10（約40%）を提案。容量の変更はすぐ反映され、すぐ戻せるとも書いていた
- 恒久対策：Terraform と実環境をそろえる、変更の経緯を確認する、apply をレビュー済みの plan 経由にする、オートスケーリングをコードで管理する（ignore_changes で Terraform と取り合わないように）、容量使用率のアラームを追加する

### 気づいたこと
- 原因は正解。直前のシナリオ2の 5xx（KeyError）を「別件」と切り分け、負荷が 2件/秒→4件/秒に増えたこと（17:10）も自分で見つけて「理由は不明」と gap に挙げていた
- 間違いが1つあった。「17:19 にトラフィックが止まり沈静化した」と書いたが、実際には負荷は流れ続けていて、スロットルのアラームも ALARM のままだった。あとで WriteThrottleEvents を取り直すと、17:18〜17:22 も毎分 189〜227 件のスロットルが続いていた（17:23 にリセットして止まった）。CloudWatch の直近1〜2分のデータはまだ届いていないことがあり、その空白を「止まった」と読んだと考えている。「WCU は 1 のままで再発の恐れ」と添えてはいたが、人が読んだら「もう収まっている」と受け取りかねない。AGENTS.md に「直近数分のメトリクスの空白は回復と見なさない」と書く候補
- 推測を1つ混ぜていた。「v1.3.0 に戻したときに古いコミットから apply し、容量も古い値に戻った可能性」。実際は意図的に下げたもので外れ。ただし「可能性」として書き、plan 全体の見直しを勧めるにとどめていた
- 提案には「事前警告アラームを追加」とあったが、実際にアラームは作られていなかった（アラームは4つのまま）。調査中に環境を変えていないことを確認した

## #4 複合シナリオ（不具合のあるリリース＋設定ミス）・スキルなし

このシナリオは「リリースを戻せば直る」と思わせるひっかけ。リリースのすぐ後に設定ミスを重ねるので、リリースだけ戻しても 504 が残る。

### 起こしたこと
- 21:42 から1秒2件（うち3割がクーポン付き）の注文を流す
- 21:45:00〜13 に `chaos.sh bad-release`（v1.4.0、FAULT_MODE=coupon_bug）
- 60秒後の 21:46:13 に `chaos.sh config-mistake`（決済タイムアウト 3000→50ms）
- 21:46:22 に `ops-lab-lambda-errors`、21:46:54 に `ops-lab-order-errors` が ALARM（`ops-lab-api-5xx` も調査中に ALARM）
- 21:47:31 に調査を開始。依頼文はアラーム名と時刻だけ

### DevOps Agent の結論（要約）
- 根本原因：約1分間隔で本番に手動変更が2件入った。1件目の v1.4.0（FAULT_MODE=coupon_bug）で KeyError → 500、2件目の SSM タイムアウト 3000→50ms で PaymentTimeoutError → 504
- 根拠：CloudTrail の2つの変更、エラーが2種類あり始まった時刻が1分ずれていること（KeyError は 21:45〜、PaymentTimeoutError は 21:46〜）、アクセスログで 500 と 504 がそれぞれの原因に対応していること、21:47 には 120件/分のすべてが失敗していたこと、DynamoDB のスロットルは 0
- 緩和策：SSM を 3000 に戻し、そのあと Lambda を FAULT_MODE なしに戻す。「片方だけ戻しても回復しない、両方必須」と明記。Terraform 側も直さないと次の apply で再発するという注意つき
- 恒久対策：calc_total の KeyError をなくす、タイムアウト値に下限を設ける（AllowedPattern か IaC での範囲チェック）、エイリアスと CodeDeploy のカナリアで自動ロールバック、変更をパイプラインに一本化して一度に1つずつ入れる

### 気づいたこと
- ひっかけに乗らなかった。エラーの種類ごとに始まった時刻を分け、「500 はリリース、504 は設定」と対応づけてから「両方戻す」と結論している
- 直前の reset（21:42 の v1.3.0 適用）もタイムラインに載せたうえで、原因からは外していた
- gap は「lambda:GetFunction の権限なし」「SSM の履歴を参照できない」「コードリポジトリ未接続」「v1.3.0 の環境変数を直接確認できない」。4回とも同じ権限不足を申告している
- 結局、スキルとルールなしで4つとも原因は正解だった。次の「スキルあり」で比べる点は、正答率ではなく、#3 のような直近メトリクスの読み違いが減るか、報告の形がそろうか、調査時間が縮むか、になる

## スキルとルールの登録（#5 から）

#1〜#4 の結果を見て、AGENTS.md とスキル `order-api-incident` に次の点を書き足してから登録した。

- 直近1〜3分のメトリクスが空でも「回復した」と判断しない。アラームの現在の状態と最新ログの時刻で確かめる（#3 の誤認への対策）
- 確かめていない仮説は「未検証の仮説」と見出しを分ける（#3 の推測への対策）
- lambda:GetFunction が拒否されたら CloudTrail の requestParameters から環境変数を読む、コードの変化は CodeSha256 で判断する（#2 で Agent が自力でやっていたことを手順にした）
- 原因が2つ以上重なっていないかを、エラーの種類ごとに始まった時刻で確かめる（#4 で Agent が自力でやっていたことを手順にした）

登録先は Web アプリの2か所。AGENTS.md は「エージェント」→ 任意のマネージドエージェント →「グローバル指示 (AGENTS.md)」にアップロード（全エージェント共通になる）。スキルは「ナレッジ」→「スキル」→「スキルを追加」→「スキルを作成」のフォームで、名前・説明・本文（frontmatter を除いた SKILL.md）を入れた。2026年11月時点で、指示の置き場所は「ナレッジ」タブから各エージェントの詳細ページに移っていた。

## #5 シナリオ3（DB の容量不足）・スキルあり

### 起こしたこと
- #3 と同じ手順。21:59 から1秒4件、22:01:12 に `chaos.sh db-throttle`（容量 5→1）
- 22:04:08 に `ops-lab-api-5xx`、22:04:54 に `ops-lab-order-errors`、22:04:59 に `ops-lab-dynamodb-write-throttle` が ALARM
- 22:06:13 に調査を開始。依頼文は #3 と同じ形（アラーム名と時刻だけ）

### DevOps Agent の結論（要約）
- 根本原因：22:01:19 に IAM ユーザーが Terraform で ops-lab-orders の書き込み容量を 5→1 に下げた。原因の層は database。「SSM とリリースの変更は原因ではなく、原因は重なっていない」と明記
- 状況：「調査完了時点でも3つのアラームは ALARM のまま、最新のエラーログは 22:07:15、継続中」
- 一次対応：Terraform の apply を止めてから容量を 5 に戻す（5 でもだめなら 10）。5 を選んだ根拠は「同じ日の 17:12〜17:23 にも同じ変更と戻しがあり、5 で正常だった」。Lambda のロールバックでは直らない（v1.3.0 で CodeSha256 も同じ）
- 仮説の扱い：「未検証の仮説：Terraform の定義に write_capacity = 1 が残っている」と、根本原因とは別の欄に分けて出した
- 恒久対策：Terraform の定義をそろえる、個人環境からの apply をやめて CI で plan をレビューする、write_capacity の下限を policy check で守る、Auto Scaling かオンデマンドを検討する

### #3（スキルなし）との比較

| 見るところ | #3 スキルなし | #5 スキルあり |
|---|---|---|
| 根本原因 | ○ 容量 5→1 | ○ 容量 5→1 |

| 推測の扱い | 「古いコミットから apply した可能性」を根拠の流れに混ぜた | 「未検証の仮説」として別の欄に分けた |
| 他の原因の除外 | 書いていない | 「SSM とリリースは原因ではない、原因は重なっていない」と明記 |
| 戻す値の根拠 | 使用率の計算から 10 を提案 | 同じ日の変更履歴から「5 で正常だった」と裏付けて 5 を提案 |

### 気づいたこと
- AGENTS.md に足した2つのルール（メトリクスの空白、未検証の仮説）が、そのまま出力に表れた。#3 の誤りは、手順を教えることで直る種類の誤りだった
- 調査時間は少し延びた。スキルの手順どおりに SSM、リリース、DB を全部確認しているためで、そのぶん「他の原因ではない」と言い切れている
- スキルに書いた JSON の報告フォーマットは、Web アプリの画面には出てこなかった。画面は調査結果を独自の形（インシデント、根本原因、緩和策、根拠の一覧）で表示するため。形式をそろえたいなら、Slack などへの通知側で使う必要がありそう
- gap は「SSM の値と履歴を取得できなかった」「Terraform のコードとコミットを確認できなかった」。lambda:GetFunction の拒否は今回は gap に出ず、CloudTrail から Lambda の設定を読んでいた

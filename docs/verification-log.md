## #1 シナリオ1（設定ミス）・スキルなし

### 起こしたこと
- 16:47 から1秒2件の注文を流し、16:48:55 に SSM パラメータ `/ops-lab/payment/timeout_ms` を 3000 から 50 に変更
- 16:50:08 にアラーム `ops-lab-api-5xx` が ALARM（変更から約70秒）
- 16:51:19 に Web アプリから調査を開始。依頼文は「アラームが鳴った、根本原因と一次対応案を調べて、環境は変更しないで」だけ

### DevOps Agent の結論（要約）
- 根本原因：16:48:55 に IAM ユーザーが Terraform 管理の SSM パラメータを手作業で 3000→50ms に上書きし、80〜400ms かかる決済が全件タイムアウトした
- 根拠として挙げたもの：CloudTrail の PutParameter、Lambda ログの「timeout_ms=50 をロード」（16:49:06）、PaymentTimeoutError の急増、アクセスログの 504、決済の所要時間は変更前後で変化なし、同じ時間帯に Lambda やデプロイの変更はなし
- 緩和策：パラメータを 3000 に戻す。Lambda の再デプロイや API Gateway の変更は不要（アプリが設定を読み直す作りであることまで把握）
- 再発防止：Terraform と実環境のずれ検知、タイムアウト値の入力制約（allowed_pattern とアプリ側の下限チェック）、Terraform 管理パラメータへの手動変更の IAM 制限と EventBridge 通知

### 気づいたこと
- スキルなしでも、設定の変更履歴までたどって正解した。直前にデプロイがない単純なケースでは、標準の調査能力で十分だった
- 調査中に「Lambda の設定を取得できない（lambda:GetFunction が拒否）」「SSM の現在値と履歴を直接確認できない」という権限の穴を、自分から gap（調べきれなかった点）として報告していた。標準の Agent Space ロールでは読めない情報があり、ログと CloudTrail から間接的に推定していた
- 「apply で戻す」を提案に含めたうえで、Terraform 側で変更を無視する設定（ignore_changes）があることには触れていなかった。コードまでは見ていないため（Agent も gap として申告）

## #2 シナリオ2（不具合のあるリリース）・スキルなし

### 起こしたこと
- 16:59 から1秒2件（うち3割がクーポン付き）の注文を流す
- 17:01:37 に `chaos.sh bad-release` を実行。Terraform で Lambda の説明を v1.3.0→v1.4.0 に、環境変数 FAULT_MODE を coupon_bug にした（コードは同じ）
- 17:02:22 に `ops-lab-lambda-errors`、17:02:54 に `ops-lab-order-errors`、17:03:08 に `ops-lab-api-5xx` が ALARM
- 17:04:01 に調査を開始。依頼文はアラーム名と時刻、「根本原因と初動・恒久対策を」だけで、リリースの話は書いていない

### DevOps Agent の結論（要約）
- 根本原因：17:01:44 に IAM ユーザーが Terraform で Lambda の設定を変え、FAULT_MODE=coupon_bug が有効になった。calc_total() の KeyError 'discount_amount' が未処理のまま 5xx になった
- 根拠：CloudTrail の UpdateFunctionConfiguration、3秒後から続く KeyError、変更前の 2 分間はエラー 0 件、CodeSha256 が直前のコード更新時と同じ（つまり変わったのは設定だけ）、DynamoDB のスロットルは 0
- 影響：17:05:43 までに 126 件の注文が失敗し、保存されていない。成功率は約75%
- 緩和策：環境変数から FAULT_MODE を消す。コードのロールバックは不要。Terraform 管理なので、CLI だけで直すと次の apply で再発すると注意書きつき。手順は「Terraform を止める → 事前確認 → 適用 → アラーム確認 → 戻し方」の5段階
- 恒久対策：Terraform から FAULT_MODE を外す、calc_total を欠損に強くして不正なクーポンは 4xx にする、未処理例外を 5xx に直結させない、障害注入フラグを本番相当から切り離す、エイリアスと CodeDeploy のカナリアで自動ロールバック

### 気づいたこと
- 「v1.4.0 のリリース」という見た目にだまされず、CodeSha256 を比べて「コードは変わっていない、設定だけ」と言い切った。これがこのシナリオで一番見たかった点で、スキルなしで正解した
- lambda:GetFunction は今回も拒否されていたが、CloudTrail の UpdateFunctionConfiguration の中身から FAULT_MODE の値を読み取っていた。ログのスタックトレースから handler.py の行番号まで特定していた
- 直前の別の出来事を、それぞれ切り分けていた。シナリオ1の名残の 5xx（16:49〜16:56、PaymentTimeoutError）は「別のエピソード」、16:58 の Base64 修正デプロイ（UpdateFunctionCode）は「その後 2 分間エラー 0 件なので無関係」と判断した
- gap として「コードリポジトリが未接続なので coupon_bug の分岐を確認できない」「変更前の FAULT_MODE の値が不明」を申告。GitHub を連携すれば、ここも埋まるはず
